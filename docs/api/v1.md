# Offtexts API — v1.2.0

The published surface every client codes against. Defined in
`supabase/migrations/0010_api_v1.sql`, extended by `0012_common_profile.sql`, `0014_category_profiles.sql` and
`0015_onboarding_hardening.sql`;
this document describes it.

**Schema:** `api_v1` · **Version:** 1.2.0 · **Status:** current

**1.1.0** (additive): `me.onboarding_completed_at`, `my_profile_details`,
`profile_details_for()`, `complete_my_onboarding()`.

**1.2.0** (additive): category answers on `my_profile_details` and
`profile_details_for()`; `religion` becomes a hideable answer, hidden by
default; `complete_my_onboarding()` also requires the purpose's answers.

```ts
// One client-wide default…
createClient(url, anonKey, { db: { schema: 'api_v1' } });

// …or per query, which is how you run two versions side by side.
supabase.schema('api_v1').from('meetings').select('*');
```

Before any of this answers, `api_v1` has to be listed under
**Project Settings → API → Exposed schemas** in the Supabase dashboard.
PostgREST refuses unexposed schemas, and the error it returns does not say
"add it to the list" — it says the schema must be one of the exposed ones,
which sends you looking in the wrong place.

---

## Why there is a contract at all

Today the clients read `public` directly. That makes every column name part of
the API: rename `meets.venue_name` and a phone app sitting in the App Store
stops working, with no way to stage the change.

`api_v1` splits the two apart. `public` is the implementation and can be
refactored freely. `api_v1` is the promise, and it only changes on the terms
below.

The clearest example is already here: the table is `meets`, because four
repositories and a domain entity are built on that name and renaming it buys
nothing. The contract publishes it as `meetings`, because that is the word
everyone actually uses. Neither has to move for the other.

### Every view is `security_invoker`

```sql
create view api_v1.something with (security_invoker = true) as …
```

Without that setting a view runs as its **owner**, which on Supabase is
`postgres`, which has `BYPASSRLS`. The view would then return every row of its
base table to anyone holding the anon key — and there is no way to put a
policy on a view to compensate, because PostgreSQL has no such thing.

One omitted setting is a full table dump. `supabase/tests/assertions.sql` fails
the build if any view in this schema is missing it, and that check has been
verified to catch a planted bad view rather than passing vacuously.

## Versioning

**The schema name carries the major version. `contract_version()` carries the
rest.**

| Change                                    | Result                            |
| ----------------------------------------- | --------------------------------- |
| Add a view, a function, a nullable column | minor bump — stays in `api_v1`    |
| Add a value to an existing enum           | minor bump — see the caveat below |
| Fix a wrong value, no shape change        | patch bump                        |
| Remove or rename anything                 | **`api_v2`**                      |
| Narrow a type, or make a column non-null  | **`api_v2`**                      |
| Change what an existing field means       | **`api_v2`**                      |

A major version is a new schema created alongside this one, with both listed
in Exposed schemas while clients migrate. PostgREST selects the schema per
request, so a phone on the old release and a phone on the new one hit the same
database at the same time, correctly, with no flag day.

```ts
await supabase.schema('api_v1').rpc('contract_version'); // '1.2.0'
```

`contract_version()` is the one thing an **unauthenticated** caller may call —
a released app needs to be able to ask whether the server still speaks its
version before it has a session.

> **The enum caveat.** Adding an enum value is additive on the server and
> breaking on the client, because a TypeScript union does not have a case for
> it. Handle unknown enum values as a default branch rather than exhaustively,
> or treat enum additions as major.

### Deprecating v1

When `api_v2` exists: announce, keep both exposed for at least one full
release cycle of the phone app, watch `pg_stat_statements` for traffic still
hitting `api_v1`, and only then drop the schema. Dropping it is what breaks
installed apps — not creating v2.

## Errors

PostgREST maps SQLSTATE to HTTP. The ones this contract raises deliberately:

| SQLSTATE | HTTP | Means                                                    |
| -------- | ---- | -------------------------------------------------------- |
| `42501`  | 403  | Not yours, not allowed, or not signed in                 |
| `22023`  | 400  | An argument is invalid (a date in the past, a bad count) |
| `23505`  | 409  | Already exists                                           |
| `23514`  | 400  | A database constraint rejected the value                 |
| `23503`  | 409  | Points at something that does not exist                  |

**`42501` is deliberately ambiguous.** "No active match with that id" is raised
both when the match does not exist and when it is not yours. Distinguishing
them would confirm the existence of a match between two other people to
somebody who is not part of it.

### The silent case

A `select`, `update` or `delete` that RLS forbids **does not fail**. It runs
and matches zero rows. Only a `with check` violation on an insert or update
raises `42501`.

This catches people out constantly. A client that treats "no error" as "it
worked" will report success for an update that changed nothing. Check the
affected count, which is why the mutating functions here return one.

## Member surface

Everything below is scoped to the signed-in caller. Not filtered in the client
— filtered by the view **and** by RLS underneath it, so the wrong caller gets
an empty result, not a leak.

### `me`

Exactly one row, or none when not signed in.

| Field            | Type                  | Notes                                                     |
| ---------------- | --------------------- | --------------------------------------------------------- |
| `id`             | `uuid`                | Also the auth user id                                     |
| `name`           | `text`                | 2–60 characters                                           |
| `headline`       | `text`                | ≤ 140, may be empty                                       |
| `bio`            | `text \| null`        | ≤ 1000                                                    |
| `city`           | `text`                |                                                           |
| `age`            | `int \| null`         | Derived from `date_of_birth` when that is set             |
| `date_of_birth`  | `date \| null`        | Must be 18 years ago or earlier                           |
| `gender`         | `gender \| null`      |                                                           |
| `interests`      | `text[]`              | ≤ 10, each 1–60 characters                                |
| `intents`        | `meet_intent[]`       |                                                           |
| `photo_urls`     | `text[]`              | **Derived.** Approved photos, in order. Never write to it |
| `verification`   | `verification_status` | `verified` is what puts you in the feed                   |
| `is_paused`      | `boolean`             | Self-service hide                                         |
| `last_active_at` | `timestamptz`         |                                                           |

`onboarding_completed_at` (1.1.0) is null until `complete_my_onboarding()` has
checked the profile. A member with it null has not finished onboarding. It
cannot be written directly: an update that changes it is refused with `42501`
(enforced since 0015).

Write through `public.profiles` (update your own row) — there is no
`update_me()`, because PostgREST's own `PATCH` already does it correctly and
RLS already constrains it.

### `my_profile_details` (1.1.0)

The common profile: surname, pronouns, hometown, languages, education, work,
lifestyle, prompts. Every column of `public.profile_details`, including
`hidden_fields` (which answers the member hides) and `onboarding_step` (the
last onboarding step saved). Write by upserting your own row in
`public.profile_details`, keyed on `member_id`.

`prompts` is a JSON array of at most three `{ "key", "answer" }` objects, each
key one of `perfect_weekend | talk_for_hours | friends_describe |
excited_about | you_should_know`, each answer 1–200 characters. The database
rejects anything else.

`hidden_fields` may contain only `last_name`, `hometown`, `institution`,
`company`, `work_location`, `religion` (1.2.0). It defaults to
`{last_name,religion}`.

**Category answers (1.2.0).** The questions that depend on the member's
purpose, all nullable, lists capped by the database:

| Purpose      | Columns                                                                                                                                                |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Dating       | `relationship_goal`, `children_plan`, `partner_values` (≤ 3 of a fixed list)                                                                           |
| Life partner | `marriage_timeline`, `marital_status`, `children_plan`, `religion`, `faith_importance`, `living_arrangement`, `family_involvement`, `open_to_relocate` |
| Co-founder   | `cofounder_role`, `startup_stage`, `founder_skills` (≤ 3), `seeking_skills` (≤ 3), `founder_commitment`, `startup_industries` (≤ 5), `funding_plan`    |

All are stored whatever the purpose, so switching purpose and back keeps them.

Every item in a text list on this view — `languages`, `career_interests`,
`skills`, `startup_industries` — is 1–60 characters after trimming (since
0015).

**Nobody else can read this view or the table behind it.** Other members go
through `profile_details_for()`.

### `my_preferences`

`member_id`, `age_min`, `age_max`, `interested_in` (`gender[]`), `intents`
(`meet_intent[]`), `cities` (`text[]`, ≤ 5), `max_distance_km`, `push_enabled`,
`email_enabled`, `quiet_hours_start`, `quiet_hours_end`, `updated_at`.

**Empty array means "no preference", not "nobody".** Every query treats an
empty array as unfiltered.

`quiet_hours_start` and `quiet_hours_end` are both-or-neither. A start with no
end is not a quiet period, it is a bug that silences someone forever.

### `my_photos`

Includes photos still in moderation, because their own member is the one person
who should see a pending photo and know that it is pending.

`id`, `url`, `storage_path`, `sort_order` (1–6), `moderation`
(`pending | approved | rejected`), `rejection_reason`, `width`, `height`,
`created_at`.

Upload to the `profile-photos` bucket under `<member-id>/<filename>`, then
insert the row. A member can insert, reorder and delete their own photos, and
**cannot** approve one: the insert and update policies both require
`moderation = 'pending'`.

### `my_availability`

`id`, `weekday` (**1 = Monday … 7 = Sunday**, ISO-8601 — the same numbering
`extract(isodow from …)` returns), `starts_at`, `ends_at`.

Overlapping windows are allowed and mean their union.

Readable by a member you have an **active** match with, and by nobody else.
Closing the match takes that access away again.

### `daily_candidates`

Today's set, and the recent ones, with the subject resolved so a client needs
one request rather than six.

| Field                                                                                    | Type                                                    |
| ---------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| `candidate_id`                                                                           | `uuid`                                                  |
| `for_date`                                                                               | `date`                                                  |
| `slot`                                                                                   | `int` — 1 is shown first                                |
| `member_id`                                                                              | `uuid` — the person being shown                         |
| `name`, `headline`, `bio`, `city`, `age`, `gender`, `interests`, `intents`, `photo_urls` |                                                         |
| `my_decision`                                                                            | `decision_kind \| null` — resume part-way through a set |

`score` and `reason` are **deliberately absent.** They are staff-facing: the
reasoning behind a recommendation is useful to somebody answering a complaint
and corrosive to show the person being recommended to.

Sets are generated nightly by `public.generate_candidates()`. An empty set is a
real answer — "we had nobody to show you today" — and is distinguishable from
the job not having run, because the set row exists either way.

### `my_matches`

`match_id`, `status`, `matched_at`, `member_id`, `name`, `headline`, `city`,
`age`, `photo_urls`, `meeting_count`.

`member_id` is always **the other person**. That is why the table stores
`member_a`/`member_b` rather than requester/recipient: a match has no
direction, and the only question a client ever asks is who the other one is.

### `meetings`

| Field                                            | Type                  | Notes                                             |
| ------------------------------------------------ | --------------------- | ------------------------------------------------- |
| `meeting_id`                                     | `uuid`                |                                                   |
| `status`                                         | `meet_status`         | `pending → confirmed → completed`, or `cancelled` |
| `scheduled_for`                                  | `timestamptz`         |                                                   |
| `duration_minutes`                               | `int`                 | 15–480, default 60                                |
| `booking_fee_paise`                              | `int`                 | **Paise.** Stamped at booking time                |
| `venue_name`, `venue_area`                       | `text`                | Derived from the cafe when one is linked          |
| `cafe_id`, `match_id`                            | `uuid \| null`        |                                                   |
| `i_requested_it`                                 | `boolean`             |                                                   |
| `with_member_id`, `with_name`, `with_photo_urls` |                       | The other participant                             |
| `confirmed_at`, `completed_at`, `cancelled_at`   | `timestamptz \| null` |                                                   |
| `cancellation_reason`                            | `text \| null`        |                                                   |
| `my_check_in`                                    | `timestamptz \| null` | The caller's own side only                        |

### `venues`

Bookable cafes only. `id`, `name`, `slug`, `address_line`, `area`, `city`,
`latitude`, `longitude`, `maps_url`, `concurrent_meet_capacity`, and `hours` as
a JSON array of `{weekday, opens_at, closes_at}`.

Contact details are **absent by design** — a member being shown a cafe
manager's personal mobile number is a data leak with a human on the other end.

A cafe open past midnight is two rows in `hours`, not a window that wraps.

### `my_notifications`

`id`, `kind`, `title`, `body`, `data` (jsonb), `read_at`, `created_at`.

### `my_payments`

Receipts. `payment_id`, `meeting_id`, `receipt`, `razorpay_order_id`,
`razorpay_payment_id`, `amount_paise`, `amount_refunded_paise`, `currency`,
`status`, `refund_coverage`, `method`, `card_last4`, `card_network`,
`captured_at`, `created_at`.

Razorpay's identifiers are here because a member ringing their bank needs them.
The gateway's error columns are not: "error_step: authorize" helps nobody and
worries everybody.

**All money is integer paise.** ₹250 is `25000`. There are no rupee decimals
anywhere in this system, because a float that does not round is how
reconciliation breaks.

## Staff surface

`staff_members`, `staff_meetings`, `staff_reviews`, `staff_reports`,
`staff_venues`.

These are readable by anyone and **return nothing without a staff row**,
because `security_invoker` keeps the policies in force. There is no separate
admin key and no separate endpoint; a non-staff caller gets an empty result
rather than an error, which is also what stops these views being a way to probe
for who is staff.

Staff membership is `public.staff`. There is deliberately **no screen and no
API** to grant it — a portal that can grant portal access is one compromised
account away from being wide open:

```sql
insert into public.staff (id, role, note)
select id, 'admin', 'Prashant — engineering'
from auth.users where email = 'prashant@example.com';
```

### The one thing staff cannot see

`decisions` — who liked or passed on whom — is readable **only by its author**.
Not by the subject, and not by staff.

Investigating a complaint does not require bulk access to who fancies whom, and
if staff could read it, that list exists behind one compromised admin account.
There is no view over it in this contract, and adding one would be a product
decision, not a technical convenience.

## Functions

All **`SECURITY INVOKER`**: every one runs as the caller, so RLS is still what
decides whether a write is allowed. A `SECURITY DEFINER` function here would be
a hole with a nice name on it.

What they add on top of RLS is the product rules RLS cannot express — "you may
only propose a meeting to somebody you have matched with" is not a
row-visibility question.

### `record_decision(p_subject_id uuid, p_kind decision_kind, p_candidate_id uuid = null) → uuid | null`

Like or pass. Returns the **match id** when this completed a mutual like, and
`null` otherwise — so a client learns about a new match from the same round
trip instead of polling for one.

Upserts: changing a pass to a like is a normal thing to do, and the match
trigger fires on the update just as on the insert.

The match itself is created by a database trigger, not by this function. Two
people liking each other in the same second is the normal case at any volume,
and an application-side "read then write" produces either two matches or none.

`42501` if the subject is not verified — you may only decide about somebody you
can actually see.

### `request_meeting(p_match_id uuid, p_cafe_id uuid, p_scheduled_for timestamptz, p_duration_minutes int = 60) → uuid`

Returns the new meeting id.

- `42501` — no active match with that id, **or** not yours
- `22023` — `p_scheduled_for` is in the past

The fee is read from `public.current_booking_fee_paise()` at booking time and
stamped onto the meeting, so a later price change never reprices a booking
somebody already agreed to.

### `respond_to_meeting(p_meeting_id uuid, p_accept boolean, p_reason text = null) → meet_status`

Confirm or decline. `42501` when there is no meeting in a state that can be
changed — which covers "not yours", "no such meeting" and "already past that
point" with one answer.

### `check_in(p_meeting_id uuid) → timestamptz`

Records the caller's own side only. One person turning up and the other not is
exactly the situation this has to be able to represent.

### `mark_notifications_read(p_ids uuid[]) → int`

Returns how many were actually marked.

### `register_push_token(p_token text, p_platform device_platform) → void`

Upserts **on the token**, not on the member: a device that moves to a different
account has to move the token with it, or one person's notifications go to
somebody else's phone.

### `file_report(p_subject_id uuid, p_category report_category, p_details text, p_meeting_id uuid = null) → uuid`

Severity is deliberately not a parameter. Triage is staff work, and asking
somebody to rate their own distress on a four-point scale is unkind and
useless.

A report cannot be edited or withdrawn after filing — a safety report is a
statement made at a point in time. Additional information is a new report.

### `set_photo_order(p_ids uuid[]) → int`

Takes the **full ordered list**, not a pair to swap: a swap needs two round
trips, and a client that fails between them leaves the order broken. `42501` if
any id is not yours.

### `profile_details_for(p_member_id uuid) → setof row` (1.1.0, 1.2.0)

Another member's common profile with their hidden answers returned as null,
and without `hidden_fields` or `onboarding_step`. Returns a row only for
yourself, or for a member who is verified **and** has finished onboarding;
otherwise no rows. Not callable without a session.

Since 1.2.0 it also returns the category answers — but only those for the
purpose the member is here for now (see the table above); the rest come back
null or empty. `religion` is returned only when it is not in their
`hidden_fields`. You always get all of your own.

### `complete_my_onboarding() → timestamptz` (1.1.0, 1.2.0)

Stamps `profiles.onboarding_completed_at` and returns it. Refuses with `22023`
and a sentence naming what is missing — date of birth, gender, purpose,
working/studying, an introduction, the purpose's required answers, or at least
two photos that are not rejected. Calling it again once complete returns the
original time.

Required per purpose (1.2.0): **dating** — `relationship_goal`; **life
partner** — `marriage_timeline` and `marital_status`; **co-founder** —
`cofounder_role`, `founder_commitment` and at least one `seeking_skills`.

### `contract_version() → text`

`'1.2.0'`. Callable without a session.

## Storage

| Bucket            | Public | Max file | Types                |
| ----------------- | ------ | -------- | -------------------- |
| `profile-photos`  | yes    | 5 MB     | jpeg, png, webp      |
| `cafe-photos`     | yes    | 5 MB     | jpeg, png, webp      |
| `report-evidence` | **no** | 10 MB    | jpeg, png, webp, pdf |

Keys are `<member-id>/<filename>` for profile photos and `<report-id>/<filename>`
for evidence; the storage policies match on that first path segment, so the
layout is load-bearing rather than a convention.

**`report-evidence` is the only private bucket**, reached through
`createSignedUrl` and never a public one. A signed URL **cannot be revoked once
issued** — tightening a policy afterwards does not invalidate links already
handed out — so expiries there should be minutes, not days.

Free plan ceiling: 1 GB total, 50 MB per file.

## Things that are not here

Stated plainly, because a contract that quietly omits things is worse than one
with gaps written down.

**No realtime.** Matches and notifications are polled. Supabase Realtime over
these tables would need its own policy review — a subscription is a read.

**No "who liked me".** See above. It is one policy away and that policy is
deliberately not written.

**No chat.** `matches` has no messages table. Whether Offtexts has in-app
messaging at all is a product decision nobody has made; the premise of the
product is meeting off text, so the honest default is that it does not.

**Nothing writes `notifications` yet.** The table, the policies and the read
path exist. What inserts a row — a trigger, a scheduled job, an Edge Function —
is not decided, so nothing does.

**Payments are modelled but not switched on.** `current_booking_fee_paise()`
returns `0` and the Razorpay integration is not deployed. Nothing charges
anybody until that function is raised by a migration. A schema ready to take
money is not a product that has started taking it.

**Candidate generation is not scheduled.** `generate_candidates()` is
idempotent per date and ready to run; whether it runs under `pg_cron`, an Edge
Function or by hand is a deployment decision. `pg_cron` availability on the
free plan could not be confirmed from Supabase's documentation, so it should be
checked in the dashboard before anything depends on it.

### Open questions for product

1. **Should booking a meeting require a match?** The RPC enforces it. The
   underlying RLS policy from `0002` does not — it allows a meet with any
   verified member, which is how the current app's Discover screen works.
   Tightening the policy would break that screen, so it has been left alone and
   flagged here rather than changed quietly. The two should agree.
2. **What is the booking fee?** `0` today.
3. **Cancellation and refunds.** How late is too late to cancel, and who gets
   their money back? The refund machinery exists; the policy does not.
4. **No-shows.** `check_in` records who turned up. Nothing acts on it yet.
5. **Does a rejected photo block a profile?** Today it is simply not published.

## Testing it

```bash
supabase/tests/replay.sh
```

Recreates a scratch database, applies every migration from empty, then runs
`assertions.sql` (8 structural rules) and `behaviour.sql` (78 checks, of which
28 are policy tests run as `authenticated` with a real subject claim).

The policy tests are the ones that matter, because an RLS mistake is silent:
the query succeeds, returns rows it should not have, and looks exactly like a
query that worked.
